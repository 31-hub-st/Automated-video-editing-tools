# StoryForge Studio Windows 使用与多电脑协同

> Hub 主机向其他制作电脑发布软件更新的流程、安全边界和 API 见 [AUTO_UPDATE.md](AUTO_UPDATE.md)。

适用系统：Windows 10/11 64 位  
适用源码版本：StoryForge Studio `v1.0.6`。当前团队验收只使用包含本机制作服务、FFmpeg、约定 TTS 组件和根目录一键恢复载荷的完整程序目录；不得用旧版单 EXE 或残缺目录代替。ZIP 名称、大小与 SHA-256 必须在真实构建后填写到 [v1.0.6 发布交付报告](V1.0.6_RELEASE.md)；报告仍有 TODO 时不得交付。

## 最简单的开始方式

1. 把整个发布文件夹解压到 `D:\StoryForge`。安装根目录必须是纯英文/ASCII、位于本地固定磁盘且当前 Windows 用户可写；不要只复制 `StoryForge Studio.exe`，也不要直接在 ZIP 压缩包里运行。
2. 双击 `StoryForge Studio.exe`，只输入成员账号和密码。发布包已预置 Hub 地址，电脑名称自动读取，设备登记与本机制作服务自动完成；无需另外安装 Python、FFmpeg，也无需运行启用脚本。
3. 若使用本地 AI 完整版，确认 EXE 同级存在 `local-ai\kokoro\config.json`、`kokoro-v1_0.pth` 和 `voices` 下随发布版提供的女声文件。当前免费本地 Kokoro 支持美式英语、英式英语、日语、西班牙语、法语、印地语、意大利语、巴西葡萄牙语和中文；缺少对应 Voice 文件时，该语种不能离线生成候选配音。轻量版不会包含这些文件，页面显示“Kokoro 还未配置”属于正常状态，可改用 Edge TTS/Deepgram 或 Kokoro HTTP 服务。
4. 首次本机检测一般需要 3–6 秒；第一次加载本地女声模型可能需要 1–3 分钟，之后会复用模型和语音缓存。
5. 在“资料库”导入小说，检查软件自动识别的语种，再建立平台、口令和可选的人工发布账号。
6. 首次启动选择本机的 `StoryForgeData` 数据目录。登录成功后可关闭 StoryForge 完整窗口，并在浏览器打开团队地址完成选书、试听、本机目录配置与批量生成；右侧即时预览确认后直接创建任务，不生成或审批中间视频文件。全部设置、缓存、日志、组件和任务工作区都应位于用户选择的 `<StoryForgeData>`。

不要放在 `Program Files`、OneDrive/网盘同步目录、网络共享、U 盘或包含中文/Unicode 字符的路径中。建议安装盘至少预留 20 GB，批量生产另为最终视频输出预留空间。日常批量生产建议 32 GB 内存和 NVMe SSD；16 GB 也能运行，但首次加载和 CPU 渲染会更慢。

## 首次完整安装与后续更新

### 第一次安装或人工修复

每台电脑第一次都必须复制同一版本的**完整发布目录**，不能只复制 EXE。轻量版的完整目录不含 Kokoro 资产；本地 AI 完整版首次启动后的目录结构为：

```text
StoryForge 发布目录\
├─ StoryForge Studio.exe
└─ local-ai\kokoro\...            # 当前日语等约定能力仍随完整包提供

<用户选择的 StoryForgeData>\
├─ components\                     # 独立语言组件包
├─ cache\
├─ render-work\
└─ updates\
```

退出旧程序后复制整个程序目录，再启动 `StoryForge Studio.exe`。不要指望自动更新补齐一个曾经只复制 EXE 的残缺安装；遇到更新中断或程序目录权限错误时，应先用完整目录人工修复。后续可选语言资源通过独立组件包装入用户选择的 `<StoryForgeData>\components`；当前完整包内置的日语链路仍可直接工作。不要把任意电脑的 `StoryForgeData` 打进核心程序交付包。

### 旧版迁移兼容

从任意 `0.x` 旧版迁移时，先等待任务结束并完全退出旧桌面端与 Worker，再把 `v1.0.6` 完整包解压到新的纯英文目录；首次启动会迁移可识别的长期数据，完成一条真实任务并由管理员确认后，才可清理旧目录。

### 主电脑发布新版

1. 开发/发布人员把 `storyforge.__version__` 提升为更高版本，完成测试、EXE 构建和离线模型导出。
2. 从已经验收的完整发布目录生成自描述更新 ZIP，入口名必须是 `StoryForge Studio.exe`。以下用占位符表示，正式发布时由构建人员替换为真实路径和 SemVer：

   ```powershell
   python .\scripts\build_update_package.py `
     "<完整发布目录>" `
     --entrypoint "StoryForge Studio.exe" `
     --version <SemVer> `
     --output "<更新包输出路径>"
   ```

3. 先备份 Hub 主电脑，再通过正式 Release 校验链把新完整程序安装到新的 `App-<version>`，但不手改 `current.json`。已有现代布局和旧参数化 ops-task 布局都显式运行 `scripts\repair_storyforge_hub_launcher.ps1 -HubRoot D:\StoryForgeHub -DataRoot D:\StoryForgeHub\Data -TargetAppDirectory D:\StoryForgeHub\App-<version>`；脚本会按布局选择受支持的原子升级或旧任务迁移。最后只在批准的维护窗口重启原计划任务并确认 Hub 正常。主电脑不会自动安装自己发布的版本。
4. 在主电脑“设置 → 软件更新”选择 ZIP，填写相同版本号和更新说明，点击发布；也可由管理员在 Hub 网页管理界面上传同一 ZIP 并发布。远程制作电脑不能通过设备 Hub RPC 发布软件。

以上流程只发布**核心程序**。语言组件包使用独立后端：清单包含 `component_id`、版本、应用兼容范围及逐文件 SHA-256，Hub 或本地发布器还可校验整包 SHA-256；客户端安全解压到 `<StoryForgeData>\components`，通过不可变版本目录和原子状态文件切换，并保留上一版回退。组件包不得替换 EXE，核心程序 ZIP 也不得覆盖组件数据。

旧 Hub 启动器修复只适用于已存在且身份完全匹配的受管部署。现代布局不传 `-TargetAppDirectory` 时，脚本保留历史修复合同：核对 `current.json`、旧启动器入口、固定 DataRoot、host 设置、catalog 文件和计划任务精确身份，只修复两个启动器到已有当前入口。

现代布局显式传入 `-TargetAppDirectory` 时，脚本会对当前与目标 App 都重算 `BUILD_RELEASE_VALIDATION.json` 完整文件树，且目标版本必须严格高于当前版本。在 host 设置、非空普通 catalog、当前两个启动器和计划任务精确身份全部通过后，先预写临时文件并重做 TOCTOU 校验，再按 `current.json` → `Start-StoryForge.cmd` → `Start-StoryForge-Hub.ps1` 的顺序原子替换；最后一个文件是计划任务实际调用的启动器，计划任务定义保持不变。替换或最终复验失败会按反向顺序逐字节回滚。

若旧机只有参数化 `Start-StoryForgeHub.ps1` 计划任务，且三个现代文件全部不存在，必须先用正式 Release 的 GitHub digest、sidecar、archive、内部 manifest 和完整目录验证链安装新 `App-<version>`，再运行 `repair_storyforge_hub_launcher.ps1 -HubRoot D:\StoryForgeHub -DataRoot D:\StoryForgeHub\Data -TargetAppDirectory D:\StoryForgeHub\App-<version>`。此路径会逐字核对旧 wrapper/task/App/Data/Port 身份，并重算新 App 的 `BUILD_RELEASE_VALIDATION.json` 完整目录摘要；仅在全部通过后生成两个现代启动器和 `current.json`、更新任务 action，失败即回滚。三种路径都不会读取或修改 SQLite，不会启动或停止服务，也不会修改 DataRoot。任何半迁移或身份不匹配状态都必须查明原因，不能用 bootstrap、新机一键恢复或 `-Force` 注册来覆盖现有正式 Hub。

`enable_storyforge_hub.ps1` 仅是旧发布目录的首次启用兼容入口：已有同名计划任务或端口监听时必须拒绝，不会覆盖。既有受管 Hub 升级后只能用 `repair_storyforge_hub_launcher.ps1`，不能重跑 enable。

### 制作电脑接收新版

1. 制作电脑必须处于“接入主电脑”模式且设备登记有效，并开启“自动检查更新”。默认每 60 秒检查。
2. 开启“自动下载”后，新版下载到用户选择的 `<StoryForgeData>\updates`，不会覆盖正在运行的程序，也不会回写旧 C 盘 StoryForge 目录。
3. 校验完成后程序会安排安全更新；正在配音、合成或完整视频渲染时继续延后，不会热替换。
4. 队列空闲并正常退出后，或下次本机制作服务启动时，外部更新器再次校验 ZIP，备份即将覆盖的文件、安装并重新打开 StoryForge。
5. 更新结果保存在 `<StoryForgeData>` 的更新状态中，核心程序回滚副本只保留一份且最多保留 3 日。失败时退出软件并用同一完整发布目录人工覆盖程序文件；保留原数据目录。

更新包不会删除安装目录中已经存在、但新版 ZIP 未包含的旧文件，所以它适合新增和替换，不适合靠“省略文件”卸载旧组件。发布与安装均必须把 `StoryForgeData` 当作不可覆盖的用户数据目录。当前局域网默认使用 HTTP；只在可信专用网络内使用，不要把 8765 端口直接暴露到公网。

## 多电脑协同：只做三步

不需要共享文件夹，也不再固定电脑数量。一台主电脑集中保存小说、口令、成员账号、任务元数据、租约和生产记录；每台制作电脑仍使用自己的 TTS、媒体执行队列、视频、音乐、字幕处理、FFmpeg 和输出目录。

### 第一步：设置主电脑

1. 选择网络稳定、会长期开机的一台电脑。
2. 打开“设置 → 多电脑协同”。
3. 选择“设为主电脑（长期运行）”。
4. 填写容易识别的电脑名称；连接端口通常保持 `8765`。
5. 保存并重启 StoryForge。Windows 防火墙询问时，只允许“专用网络”。
6. 点击“检查连接”，记下主电脑显示的团队访问地址，例如 `http://192.168.1.20:8765`。这个地址可填入其他电脑的 StoryForge“设置 → 多电脑协同”，也可在普通浏览器打开团队资料与管理页面；浏览器不是本机媒体 Worker。
7. 启用 Hub 后台任务。源码目录运行 `scripts\enable_storyforge_hub.ps1 -DataRoot <正式固定数据目录>`；正式发布时使用发布目录提供的 Hub 后台入口。`DataRoot` 必须与当前 Hub 的 `settings.json` 和正式 catalog 所在目录一致。系统会注册当前用户的 `StoryForge Hub` 登录任务；此后关闭桌面窗口不会停止网页服务，异常退出后会自动重试。
   StoryForge 会在主机同时存在虚拟网卡、VPN 或沙箱网卡时优先选择 `10.x`、`172.16–31.x`、`192.168.x` 的真实局域网地址，避免把 `198.18.x.x` 等不可供制作电脑访问的测试网段显示出来。

无需安装 StoryForge 的电脑可直接打开上述 Hub 地址，用成员账号和密码维护/查看获准资料、准备草稿、查看浏览器即时预览、生产记录和产物元数据。它不能播放或下载员工电脑上的本地成片。需要试听、选择本机素材、打开本机成片或生成视频时，当前员工电脑必须安装完整发布目录、完成一次账号绑定并启用本机制作服务；此后员工可以继续使用同一个 Hub 网页，不要求完整桌面窗口常开。详细边界见 [网页端使用说明](WEB_ACCESS.md)。

### 第二步：建立成员账号

打开“设置 → 成员账号与权限”，为每个人选择一种角色：

- 管理员：管理资料、口令、批次、生产记录、成员账号和多电脑协同。
- 员工：制作自己的任务，查看和重试自己的记录；可维护个人制作默认值、当前电脑运行环境和本机更新，不能修改小说口令、团队、Hub 或密钥设置。

一般不需要打开“高级权限”。只有个别员工需要临时承担额外工作时，才为该账号选择“额外开放”或“禁止使用”。

从旧版升级时，原“主管”账号会安全转换为员工，并把原先比员工多出的权限保留为账号级特殊权限，不会自动获得管理员权限。多电脑协同环境请先升级并重启主电脑，再在制作电脑上编辑这些旧账号。

从“设置 → 成员账号”建立账号。新员工默认密码为 `xs123456`；首次登录后建议修改但不强制，也不作为接入验收门槛。产品不提供员工可见的登录令牌功能。

### 第三步：接入制作电脑

1. 在其他电脑上复制管理员提供的完整 StoryForge 发布文件夹；该文件夹已包含当前团队的 Hub 地址。
2. 双击 `StoryForge Studio.exe`。
3. 只输入成员账号和密码并登录。软件自动读取 Windows 电脑名称、登记这台电脑、安全保存内部设备凭据并启用 `StoryForge Local Worker`。
4. 刷新 Hub 网页。顶部显示当前电脑且运行环境能读取本机 FFmpeg/TTS 后即可开始制作。

正常流程不显示也不接受人工令牌。发布目录中的 `admin-tools\enable_storyforge_worker.cmd` 仅供管理员在后台服务损坏时维修，不应作为员工操作步骤。

主电脑会用任务租约和心跳避免同一个任务被重复领取。某台电脑失败不会停止其他任务；主电脑暂时断开时，已经领取的渲染可以继续，但不要在断网期间修改共享小说资料或创建新的共享批次。

### 制作电脑本地网页与 Hub 浏览器边界

- 制作电脑的本机制作服务负责本机 Kokoro/Edge/云 TTS 调用、候选配音生成、本机视频/音乐/输出目录、完整任务建队、队列控制、失败重试和 FFmpeg 渲染。操作界面可以是桌面窗口、连接本机制作服务的 Hub 页面，也可以是该电脑的 loopback 本地网页；服务启用后完整窗口无需常开。
- Hub 浏览器负责登录、团队资料与账号管理、受控共享资料上传、小说/平台/口令维护、题材分析、草稿准备与保存、HTML/CSS 即时预览，以及查看任务记录、产物元数据和校验。只有页面所在员工电脑连接自己的 Local Worker 时，才可打开该电脑的本地成片；管理员不能经 Hub 读取其他员工电脑的文件。
- `storyforge.web.WEB_DESKTOP_ONLY_MEDIA_METHODS` 会阻止 Hub 主机进程直接执行媒体调用。Hub 页面在制作电脑上会经短时票据连接 `127.0.0.1:18765–18770`；loopback 页面直接调用同一台电脑的本地 API。两条路径都开放完整生产白名单，但不开放历史 preview 审批方法。
- 因此需要实际出片的每台电脑都必须复制完整发布目录并至少打开 EXE 登录一次。只打开 Hub 地址且没有完成自动本机服务配置的电脑不会使用自己的显卡、素材盘或 Kokoro 运行时进行渲染，也不会把媒体压力转移到 Hub 主机。

## 标准生产流程

1. 在“资料库 → 小说资料”导入或粘贴 TXT/DOCX；软件按正文自动识别语种，资料库可按实际语种筛选。低置信度、混合或未识别结果请先人工确认；重复正文会提示复用，修改正文会建立新版本。正文存在显式 `Chapter`、`Episode`、`Part` 等分集标题时，每个分集保持为独立可选单位，短集不跨章合并；资料库导入阶段可把预计超过 10 分钟的原始长分集在完整句子和悬念处规划为可选子段，没有显式标题时才按全文规划可选段。员工在制作台自行勾选要合并的分集/子段；本批合计超过 10 分钟只提醒，仍生成一条连续视频，不自动拆分。资料库优先显示已上传的小说封面，没有封面时才显示占位图。
2. 在“资料库 → 平台与口令”维护平台模板、平台 Logo 和品牌色，并为小说绑定平台和历史口令。每个“小说 × 平台”历史累计最多 5 个口令。主电脑会把 Logo 复制到 Hub 附件目录，制作电脑在渲染前自动取得本地副本；不要把平台 Logo 当作某一本小说的封面。
3. 在“资料库 → 发布账号”登记人工发布账号；本批也可以保持“待分配”。资料库只维护长期固定资料，不保存某次生产的女声、字幕或素材选择。
4. 进入“制作台”，点击小说选择区域打开可视小说库；可以按书名或题材名称搜索，并按平台、语种筛选，卡片显示小说封面、标题和分类。选定小说后，再选择本批平台和口令、发布账号、一个或多个分集/子段及生成总视频数。所选内容按正文顺序合成一条连续视频的内容单元，再按总数制作去重版本，不按分集分别成片或均分数量。选择从第 1 集开始时无上集回顾；从后续集开始时只在整组开头回顾一次。生成数量不设业务上限。
5. 选书时软件使用当前文本服务分析简介和正文抽样，自动建议题材，用于内容、女声和音乐参考；服务不可用时回退到本地规则。**视频素材不按题材匹配**，员工直接选择本批视频素材文件夹，系统只递归扫描该文件夹。免费本地 Kokoro 可直接试听和制作约定语种；当前完整包内置日语前处理和 Voice。Edge TTS 需联网并覆盖更多语种，候选数量以当前真实可用女声为准，不虚构第三个 Voice。
6. 选择视频模板：“经典模板”保持传统顶部口令卡；“平台简介卡”前 5.5 秒显示钩子标题、平台 Logo、品牌色、精确口令和真实小说简介/正文摘录，使用简洁的社交平台信息卡布局，随后保留搜索卡和语义短语字幕。只有当前正文版本真正的最后一集才显示 `FINAL PART`，选中批次中的最后一项不等于全书最后一集。“使用小说封面结尾”默认开启，开启时最后 5–7 秒由小说真实封面以所选动效铺满全屏；关闭时保持正文画面收尾。两种模式都继续朗读并显示 CTA，不再叠加白色平台结尾卡，顶部搜索口令持续显示。模板、WPM、音乐音量、字幕、封面开关/动效、渲染模式及本机目录都只属于本批，不会改写小说固定资料。
7. 在制作台右侧切换“开头 / 正文字幕 / 封面结尾”即时预览。该预览由界面实时绘制，不产生 MP4、WAV 或 ASS，也没有审批环节；修改设置后保存草稿即可刷新冻结方案。
8. 在制作电脑的桌面窗口、Hub 网页或本机制作网页点击生成。本机一次创建全部 `job_kind="full"`、`status="queued"` 任务并返回 `preview_required=false`，随后自动执行；失败任务会被跳过，其余任务继续。系统只递归读取员工本批选择的视频素材文件夹；其中没有可解码视频时才失败，不再要求或推断题材目录。三种制作方式分别是：兼容接口值 `video_and_mp3`（常规视频生成）只交付 H.264、1080×1920、默认 60 FPS 的 MP4；`audio_only`（仅生成配音）只生成一份 MP3；`reuse_audio`（已有配音更换素材）读取带可靠字幕索引的配音 MP3，以新的本机视频素材只生成 MP4。视频固定速度支持 0.8–3.0×，素材不足时先使用不同素材再复用；背景音乐可自动、手动或关闭。员工发布目录按模式只平铺最终 MP4 或 MP3；Manifest、日志、ASS、内部 WAV、恢复日志和缓存位于 `<StoryForgeData>\render-work\<批次>\<任务>\`。Hub 永不上传这些生产媒体，只保存元数据、校验和本机引用。
9. 提交成功后，上一批配置被冻结并继续后台制作，制作台立即进入一个新的未保存草稿。女声、WPM、音乐音量、字幕/画面样式、封面动效、渲染模式以及本机视频、音乐和输出目录会保留；口令、发布账号和分集会清空，必须为下一批重新选择。无需等待当前批次结束，可以反复提交新批次。
10. 同一制作电脑严格按提交顺序 FIFO 执行批次：前一批的全部任务（包括未装入内存的超大批次尾部）处理完后才开始下一批。单条失败写入原因并成为终态，队列继续执行同批剩余任务和后续批次，不会因失败整队停住。
11. 制作台任务胶片带按稳定 `batch_id` 显示折叠的“批次卷宗”；每批拥有独立的持久化总数、状态计数和总体进度。展开卷宗查看单视频进度、失败原因和操作，或跳转到完整生产记录。网页只显示当前任务窗口时，卷宗仍以数据库汇总为准，不用可见卡片数推算整批总数或完成状态。归档/恢复按批次组织，但不会移动或删除员工电脑本地文件。
12. 人工发布后可回填发布账号；当前版本不会登录或上传 TikTok。

## 不同地点的电脑

不同地点可以运行相同 EXE，但当前不自动同步两个地点的制作记录。最简单的方式是每个地点选择“单机使用”，或各自建立一台主电脑。不要把 StoryForge 端口直接暴露到公网；确需跨地点连接时，应先使用可信 VPN 并单独评估访问控制。

## 数据、日志、备份与卸载

- 员工全部运行数据：用户首次选择的 `<StoryForgeData>`。
- 桌面启动与运行日志：`<StoryForgeData>\logs`；逐句语音缓存：`<StoryForgeData>\cache\tts`；可选语言组件：`<StoryForgeData>\components`。
- 任务工作区与详细错误：`<StoryForgeData>\render-work\<批次>\<任务>\`；优先提交其中的 `job-error.log`、`render-error.log` 和命令/Manifest 给管理员。
- 主电脑备份其实际选择的数据目录；员工机最终 MP4、仅配音模式的 MP3 和自选素材目录不属于 `StoryForgeData`，按业务需要另行备份。
- Hub 固定资料备份保留 72 小时且最多 3 份；相同内容按摘要去重，不重复生成。备份包含固定资料库、设置、Provider 用量、团队预设和共享资料附件，不包含员工电脑的视频素材、最终 MP4/MP3、内部 WAV、ASS、字幕对齐文件或渲染缓存。
- 服务 API Key 和自动登记的设备凭据由当前 Windows 用户加密保存，不在界面回显。
- 电脑遗失或不再使用时，在主电脑打开“设置 → 多电脑协同”，停用对应设备；下一个本地网页请求即会失效。重新接入只需再次使用账号密码连接。
- 卸载当前版本时，先退出 StoryForge 与 Worker，再删除程序目录；是否删除用户选择的 `<StoryForgeData>` 必须单独确认。员工另行选择的视频素材、音乐和输出目录不会随之删除。
- 从旧版迁移过来的电脑可能仍保留旧 C 盘目录。必须先完成 `v1.0.6` 真机冒烟验收，再由管理员归档或删除；不要把旧目录继续作为活动数据使用。

## 常见问题

- **一直显示“正在检查本机”**：正常约 3–6 秒。超过 15 秒时，更新显卡驱动并重启软件。
- **第一次配音很久**：首次模型预热可能需要 1–3 分钟；之后相同文本、女声和语速会复用缓存，速度明显加快。
- **其他电脑生成日语候选配音失败**：先确认使用当前完整程序包，而不是旧版单 EXE；当前包内置日语所需前处理、字典和 Voice。若是后续独立语言组件，则在 `<StoryForgeData>\components` 检查当前/上一版状态并重试或回退，不要手工把半包文件混入程序目录。
- **日语分集只显示 0–2 秒**：这是旧版只按空格英文词计数造成的历史估算错误。当前 Catalog Schema 7 会按汉字、假名、韩文和泰文脚本重新计算当前正文版本的预计时长，同时保持分集 ID、正文和顺序不变；升级后请完整退出并重新打开 StoryForge 触发迁移。
- **制作电脑或网页无法连接**：先在主电脑任务计划程序确认 `StoryForge Hub` 正在运行；源码部署可运行 `scripts\enable_storyforge_hub.ps1 -DataRoot <正式固定数据目录>`。再确认电脑处于同一局域网/专用网络，地址使用主电脑局域网 IP，端口 `8765` 未被防火墙阻止，且成员账号和设备均为启用状态。浏览器打开根地址会进入登录页；若显示 `ERR_CONNECTION_REFUSED`，说明主机服务没有监听或被防火墙拦截。
- **Hub 网页提示“未连接本机制作服务”**：这是当前电脑没有可用媒体运行时，不是普通业务权限不足。重新打开完整 StoryForge，使用账号密码登录一次并刷新网页；软件会自动修复后台服务。仍失败时再由管理员运行诊断或维修脚本。
- **网页显示 FFmpeg 缺失**：页面读取当前电脑本机制作服务的状态，不读取浏览器或 Hub 主机。先确认连接的是正确电脑；若服务已连接仍缺失，运行 `admin-tools\diagnose_storyforge.cmd` 检查发布目录。
- **网页显示 Kokoro 还未配置**：若本机制作服务说明当前是轻量版，这属于正确状态。轻量版不含 Kokoro/PyTorch，改用 Edge TTS/Deepgram、配置 Kokoro HTTP 地址，或安装本地 AI 完整版。完整版还要核对 `local-ai\kokoro` 模型、配置和对应 Voice 文件。
- **硬件编码失败**：软件会自动切换 CPU 快速模式并记录原因；更新 NVIDIA、Intel 或 AMD 驱动通常可恢复硬件编码。
- **某条任务失败**：生产记录会保留失败阶段和日志，其余任务继续。修复素材或服务后，只重试失败项。

## 发布文件夹检查

离线版不是单文件交付。复制到每台电脑后至少检查以下项目：

```text
StoryForge 发布目录\
├─ StoryForge Studio.exe
└─ local-ai\kokoro\
   ├─ config.json
   ├─ kokoro-v1_0.pth
   └─ voices\
      ├─ af_* / bf_*                    # 美式/英式英语
      ├─ ef_dora / ff_siwis             # 西班牙语/法语
      ├─ hf_* / if_sara                 # 印地语/意大利语
      ├─ jf_* / pf_dora                 # 日语/巴西葡萄牙语
      └─ zf_*                           # 中文
```

从源码运行或自行构建本地 AI 版时，应安装完整的 `requirements-ai.txt`，不要只安装 `kokoro`。日语前处理使用 Windows/Python 3.12 可安装的 `pyopenjtalk-plus` 兼容包；所有目标电脑必须使用同一套依赖和离线 Voice 资产。

发布方若提供 SHA-256 清单，应以本次构建目录内的清单为准，不要使用旧版本固定大小或摘要。单文件校验命令：

```powershell
Get-FileHash -Algorithm SHA256 '.\StoryForge Studio.exe'
```

在新电脑上可先运行不打开界面的本地女声自检：

```powershell
& '.\StoryForge Studio.exe' --kokoro-self-test '.\kokoro-check'
```

成功时目录中会生成 `kokoro-self-test-0001.wav`（同名前缀）和 `kokoro-self-test.json`；自检会绕过业务语音缓存，确保真正执行一次新合成。失败时查看同目录日志，优先检查 `local-ai\kokoro` 是否完整。
